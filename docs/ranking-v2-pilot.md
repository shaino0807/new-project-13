# 排行榜第二版與 250 檔效能試跑

更新日期：2026-08-26

## 使用者要的真正排行榜

正式排行榜的母體不是固定 64 檔。流程固定為：

1. 先讀取完整上市、上櫃公司目錄，排除興櫃。
2. 為母體中的每家公司建立一次共同特徵資料。
3. 低估、高估、成交活躍、現金流、成長及小資六種排行榜，各自使用自己的主分數獨立排序。
4. 每種排行榜各取自己的前 64 名。

排序相同分數時依序比較：資料覆蓋率、報價日期、股票代碼。任何正式名次都必須同時具備主分數、報價日期、至少 60% 資料覆蓋率，而且沒有過期資料。

## 已修正的舊問題

- 舊發布流程雖然分批掃描市場，最後卻只拿「各榜暫存前 40 名的聯集」發布，因此無法從完整母體誠實選出每榜前 64 名。
- 新流程在發布前重新讀取所有已保存的公司特徵，再讓六種排行榜各自排序及取前 64 名。
- 正式門檻由舊 55% 統一為 60%，並加入無過期資料條件。
- 排行快照保留產業、漲跌、資料覆蓋率、過期資料、信賴狀態、報價日期及更新時間。
- 首頁改讀已完成快照，不再因訪客開啟首頁而執行 `/api/workbench` 的 64 檔重算與回測。
- 未指定自訂股票清單的舊 `/api/screener` 路徑也改為讀取已完成快照；只有明確送入自訂清單時才會做同步研究批次。

## 250 檔試跑怎麼選

250 檔只用來驗證資料成本及效能，不是正式全市場排行榜。

試跑先一次讀取 TWSE 與 TPEx 的官方全市場日行情，以最新成交金額在各市場內分成高、中、低三個流動性層級；若當日行情找不到該公司，會誠實標成「無可用流動性資料」。接著依「市場別＋官方產業＋流動性層級」分桶，每桶至少選一個固定代表，再以系統化間距從剩餘公司補足 250 檔。輸入順序即使顛倒，也會選到相同名單。

流動性分層只需兩次官方批次請求，不必為了選樣本先逐檔抓取 1,985 次報價。成交金額缺漏時，才以成交量乘收盤價作備援；兩者皆缺時不補造資料。

2026-08-26 唯讀檢查公開公司目錄：

- 上市：1,133 家
- 上櫃：852 家
- 上市＋上櫃：1,985 家
- 興櫃：535 家，這一階段排除
- 250 檔樣本：上市 139、上櫃 111，涵蓋 65 個「市場別＋產業」分桶
- 樣本流動性層級：高 62、中 70、低 74、無可用資料 44

## 本機試跑結果

執行：

```powershell
node scripts/ranking-v2-pilot.mjs --live-universe
```

已通過：

- 250 個代碼皆不重複，而且全部來自目前 1,985 家上市、上櫃公司目錄。
- 顛倒公司目錄輸入順序後仍得到同一份 250 檔樣本。
- 六種排行榜各自從 250 檔取 64 檔，合成資料下六種成分集合皆不同。
- 55% 覆蓋率或含過期來源的合成資料不會進入正式名次。
- 1,000 次「250 檔資格過濾＋六榜排序」本機 CPU 約 0.20 秒，平均每次約 0.20 毫秒；因此真正瓶頸是外部資料讀取，不是排序運算。

這個本機數字不能當成 250 檔真實資料抓取時間。它只證明母體選樣、門檻與排序邏輯能重現。

## 遠端 250 檔實測的安全邊界

後端已支援建立 `pilotSize: 250` 的工作。試跑會保存工作進度與特徵批次，量測：

- 分批數及股票嘗試次數
- 成功、失敗與重試數
- 實際評分工作時間
- 每次股票嘗試平均時間
- 真正送出的外部 HTTP 請求數、成功數、失敗數及回應資料量
- 各資料供應者的請求數、失敗數及資料量
- 共用快取與同批進行中請求的命中次數
- 有分數、報價日期、60% 覆蓋率、無過期資料及最終可列入排名的完整率
- 依目前速度推估 1,985 檔所需時間

試跑完成後只產生明確標示為 `pilot-only` 的結果，不會啟用或取代公開正式排行榜，也不會更新公開產業快照。

外部請求計數已放在共用請求層：只有真正送往供應者的 HTTP 請求才計入總數，快取與同批共用中的請求另外計數，不會把邏輯上的重複讀取誤算為新增流量。1,985 檔推估會保留固定的目錄與全市場行情成本，只放大逐檔評分部分。

本次核准範圍包含一次 AppDeploy 250 檔遠端實測，但不包含完整 1,985 檔掃描、GitHub 推送或 GitHub Pages 更新。實測數字與擴張建議會另寫入遠端試跑報告。
